# 設計

## 方針

- **リアルタイム経路はローカルで完結**させる。カメラ映像 → MediaPipe → 座標化 → ソルバー → VRM 描画は
  毎フレーム（30〜60 fps）ブラウザ内で処理し、ネットワークを待たない。
- **Gemini は「遅いが賢い」並列ループ**として使う。表情・ジェスチャー・背景・小道具・外見・声といった
  意味的な判断を担当し、結果はイベントとしてリアルタイム経路に合流させる。Gemini が止まっても
  トラッキングは止まらない。
- 各段は**差し替え可能なインターフェース**で区切り、機能追加はプラグインとして行う。

## リアルタイム経路（ブラウザ）

```
FrameSource ──▶ TrackerHost ──▶ CoordinateSpace ──▶ MotionSolver ──▶ MotionSmoother
(カメラ/動画)    (Pose→Face→Hands)  (座標化・ミラー・      (Body/Face/Hand)    (One Euro・
                                   キャリブレーション)                         アイドル復帰)
                                                                              │
          AvatarRig ◀── Plugin.update ◀── GestureLayer ◀── ExpressionMixer ◀──┘
          (VrmAvatar)    (小道具など)      (頷き・手振り・呼吸) (追跡表情 + AI ヒント + 口パク)
```

| 段 | ファイル | 入力 → 出力 |
| --- | --- | --- |
| 0. 取得 | `src/capture/FrameSource.ts` | カメラ / 動画ファイル → `HTMLVideoElement` |
| 1. 検出 | `src/tracking/*` | 映像 → `TrackingFrame`（顔 478 点＋52 ブレンドシェイプ＋変換行列、姿勢 33 点、手 21 点×2） |
| 2. 座標化 | `src/coords/CoordinateSpace.ts` | カメラ座標 → アバター座標 `AvatarSpaceFrame`（+X=アバターの左、+Y=上、+Z=視聴者側） |
| 3. 解決 | `src/solver/*` | アバター座標 → `MotionFrame`（VRM 正規化ボーンのローカル回転＋表情） |
| 4. 平滑化 | `src/solver/MotionSmoother.ts` | One Euro フィルタ、見失った骨はアイドル姿勢へ戻す |
| 5. 合成 | `src/avatar/ExpressionMixer.ts`, `GestureLayer.ts` | AI ヒント・口パク・ジェスチャーを重ねる |
| 6. 描画 | `src/avatar/VrmAvatar.ts`, `src/avatar/HairPhysics.ts`, `src/render/Stage.ts` | three-vrm の正規化ボーンへ適用し、揺れ物（髪）を固定刻みで進めて描画 |

### 座標化の要点

- MediaPipe のカメラ座標（x=画像右、y=下、z=奥）からアバター座標へは、非ミラー時は X 軸まわりの
  180° 回転 `(x, -y, -z)`。ミラー時はさらに X を反転し、左右の名前（ボーン・ブレンドシェイプ・手）を
  入れ替える。
- 頭の回転は FaceLandmarker の顔変換行列から取り出し、ミラー時は四元数 `(x, -y, -z, w)` に変換する。
- 「正面キャリブレーション」はカメラの設置角 `C` を記録し、すべてのベクトルと回転に `C⁻¹` を掛ける。
- 上半身や全身が映る構図では顔が小さく、MediaPipe の近距離顔検出が効かない。そのため姿勢ランドマーク
  （鼻・目・耳）から頭部を切り出して拡大し、顔だけを追跡する（`FaceTracker` の ROI 切り出し）。

### 左右の手の識別

`HandIdentityTracker`（`src/tracking/HandIdentity.ts`）が、検出された手のどちらが左右かを毎フレーム決める。
手首だけでなく、親指（CMC・先端）、人差し指の付け根、小指（付け根・先端）を**アンカー**として次の 3 つの手がかりを組み合わせ、最も安い割り当てを選ぶ。

1. 姿勢モデルが推定した、左右それぞれの手首・親指・人差し指・小指の位置との一致
2. 前フレームのアンカー位置との連続性（相手側の手に似ている場合も減点する）
3. MediaPipe の手の見た目による左右判定

確立した左右を入れ替えるのは、反対の割り当てが 6 フレーム続けて勝ったときだけにする。重複検出の判定も全アンカーで比べるので、手首を合わせた両手が 1 つにまとめられることはない。

姿勢モデルが手首を見られない側には高いコストを与える（0 にはしない）。これで、見えている手が隠れている腕に割り当てられることはない。
腕の側でも、手が検出されていても、姿勢がその手首をまったく見ていない腕は動かさない。

### 実カメラで入れた安定化（`src/solver/Stabilizers.ts` ほか）

- 無表情ベースライン: ブレンドシェイプの「その人の無表情時の値」を学習し、そこからの変化だけを表情として扱う
- 回転スパイク除去: 1 フレームだけ大きく飛ぶ頭の回転を捨てる
- ヒステリシス: 胴・腕・脚の追跡の開始と終了に別々の閾値を使い、画面端でのちらつきを防ぐ
- 頭はワールド空間で平滑化し、平滑化済みの胴に対する相対回転として求める。胴の揺れが顔に伝わらない
- 顔を見失っている間は、姿勢の耳・目・口から頭の向きを推定して補う
- 肘が画面外にあり手が見えているときは、肩と手首から 2 ボーン IK で肘を復元する
- カメラ映像自体が左右反転している場合の補正。新しいカメラを初めて使うときは、画面上の案内に従って右手を上げると自動で判定し、カメラごとに保存する

### ソルバーの要点

- 腕と脚は**ヒンジ平面分解**で解く。上腕のねじれを「上腕と前腕が張る平面の法線＝肘の回転軸」に
  合わせることで、肘・膝が純粋な蝶番になり、捻れの破綻が出ない。伸びきって平面が定まらないときは、
  直前に得た回転軸を使う。
- 胴は肩の線と腰→肩のベクトルから基底を作る。腰が映っていない場合は鉛直方向を上として扱う。
- 手首は手のランドマーク（手首→中指付け根、小指→人差し指）から求める。手が検出できないときは
  姿勢の手首・人差し指・小指から粗く推定する。
- 指は関節ごとの曲げ角を、レスト姿勢の曲げ軸まわりの回転として適用する。

### 髪の揺れ（`src/avatar/HairPhysics.ts`）

モデルが持つ揺れ物（VRMC_springBone、VRM 0.x の secondaryAnimation）を three-vrm の実装のまま使い、
その上で次の 3 点を加える。対象は特定のモデルに依存しない。

- **60 Hz の固定刻み**: three-vrm は `dragForce` を呼び出し 1 回ごとに掛けるため、描画フレームごとに進めると
  144 Hz の画面で髪が硬く、30 fps で柔らかくなる。物理だけを固定刻みで進め、長い停止の後は追いつかずに捨てる。
  `vrm.update()` からはスプリングを外し、`HairPhysics` だけが進める。
- **揺れの大きさ**: 髪の関節だけ、剛性を「骨の長さあたり」で上限を設け、抵抗にも上限を設ける。VRM の関節は親の向きに
  引き戻されるので、全関節を同じだけ柔らかくすると房が丸まって折れる。そこで房の根元だけを大きく緩め、先へ行くほど
  硬く・抵抗を大きくして、房全体が振り子のように揺れるようにする。作者の値より硬く・重くはしない。0 で作者の値に戻る。
- **風**: 外力（gravity）の枠に時間変化する風を足す。房ごとに同じ力を、房のしなやかさ（Σ 1/剛性）で割って与えるので、
  どのモデルでも房の先の曲がりは風の強さにほぼ比例し、曲がりは根元に集まる。

髪の関節はボーン名（`hair`、`髪`、`もみあげ` など）で見分け、名前に手掛かりがないモデルでは頭の下の揺れ物をすべて髪とする。
服や小物の揺れ物は作者の設定のまま、固定刻みだけを適用する。読み込み直後（VRM 0.x の 180° 回転と A ポーズの適用の後）に
スプリングを初期化し、T ポーズ由来の古い状態で髪や袖が跳ねないようにする。

## Gemini 並列ループ

サーバー（`server/`）が API キーを保持し、ロールごとにモデルを割り当てる。割り当ては
`config/models.json` の候補順で決まり、その API キーの `models.list` で最初に見つかったモデルを使う。
環境変数 `VTUBER_MODEL_<ROLE>` で上書きできる。

| ロール | 既定モデル | 用途 | 経路 |
| --- | --- | --- | --- |
| live | gemini-3.1-flash-live-preview | マイク＋カメラ（1 fps）を常時送信。ツール呼び出しで表情・ジェスチャー・背景・テロップを演出し、音声で応答する | `/ws/live` 中継 |
| reactor | gemini-3.5-flash-lite（思考 MINIMAL） | 数秒ごとにフレームを渡し、感情・ジェスチャー・字幕を JSON で受け取る | `/api/react` |
| spatial | gemini-robotics-er-2-preview | 手に持った物体の点・矩形（0〜1000 正規化）と構図を得る → 手に小道具、全身モード自動切替 | `/api/spatial` |
| designer | gemini-3.1-pro-preview | 読み込んだサンプルの**実マテリアル名**を前提に、ペルソナ・色・小物・テクスチャ改変指示を構造化出力 | `/api/design` |
| transcriber | gemini-4-neon | キャラクター画像を読み取り、近い素体を選び、素体のテクスチャを見ながら書き起こしの仕様を構造化出力 | `/api/transcribe`, `/api/design`（`mode: transcribe`） |
| image | gemini-3-pro-image | テクスチャアトラスを **UV 配置を保ったまま**描き換える（書き起こしでは参照画像も渡す）。設定画の生成 | `/api/texture`, `/api/concept` |
| imageFast | gemini-3.1-flash-image | 配信背景（Live の `set_scene` にも対応） | `/api/background` |
| tts | gemini-3.8-flash-tts | ペルソナの声で台詞を読み上げる（口パク連動） | `/api/tts` |
| general | gemini-3.8-flash | 汎用（予備） | — |

AI の結果は `AppEvents`（`ai:expression` / `ai:gesture` / `ai:scene` / `ai:caption` / `ai:spatial`）として
EventBus に流れる。Live・リアクター・手動操作のどれが発生源でも、同じ経路でアバターに反映される。

## 3D モデル：サンプルの取り込みと踏襲

- 既定は VRM コンソーシアムのサンプル（`VRM1_Constraint_Twist_Sample`：VRoid 標準構造、
  `Seed-san`）を `npm run setup` で取得し、そのまま読み込む。手持ちの `.vrm` もドラッグ＆ドロップで使える。
- デザイナーは、サンプルが持つマテリアル構造（例 `Hair_00_HAIR`、`Tops_01_CLOTH`）をそのまま Gemini に
  渡す。そのため改変指示は常に実在のマテリアルを対象にする。テクスチャは元のアトラスを編集し、
  元のサイズとアルファを保って差し替えるので、UV やメッシュには手を加えない。
- 小物（猫耳・ヘッドホンなど）は頭ボーンに付ける。大きさと位置はモデルのバウンディングボックスから
  算出する。
- VRM 0.x のモデル（例: 桜田 史利矢）は自身の座標で -Z を向いており、`rotateVRM0` で 180° 回す。そのため
  three-vrm の正規化ボーンの軸も 180° 回っている。`VrmAvatar` は MotionFrame（VRM 1.0 の規約）の回転を
  `(-x, y, -z, w)`、腰の移動を `(-x, y, -z)` に変換して書き込み、`getBoneNode()` は 1.0 の軸に戻した子ノードを
  返す（小物・小道具の向きを保つ）。

## 画像から書き起こし（`DesignerPlugin`、`server/gemini/transcribe.ts`）

```
参照画像 1〜4 枚 ──▶ /api/transcribe（Neon）──▶ 素体の選択 + 外見の分析（色は #rrggbb）
                                                   │
       素体を読み込む ◀────────────────────────────┘
            │
            ▼
/api/design（mode: transcribe、Neon）── 参照画像 + 素体のマテリアル一覧 + 各アトラスの縮小画像
            │
            ▼ AvatarStyle
  recolors（手元で色の置き換え）  textureEdits（/api/texture、Nano Banana Pro + 参照画像）  小物・ペルソナ
```

- 素体の選択は、髪の長さとシルエット、体格、服の形の順に見る。候補は同梱サンプル 3 体と、自分の `.vrm` を読み込んでいれば「今のモデル」
- 2 回目の呼び出しでは、各アトラスの縮小画像を「テクスチャ: マテリアル名」の見出し付きで渡す。Neon はどの島に何が描かれているかを見て、パーツごとに指示を書く
- **色の置き換え**（`TextureOps.recolorPixels`）は画像生成を使わない。基準色は「色の付いた部分の中央値」（彩度で重み付けした CIELAB の中央値）。瞳のアトラスの黒い背景や、肌に入った線に引っぱられない。各テクセルは基準色との差を保つ。明るさは差のまま（黒や白で頭打ちになる分だけ縮める）、彩度は比で（灰色のハイライトや線は灰色のまま）、色相は小さなずれ（頬の赤み）を残す。`tipColor` で、アトラスの上端（根元）から下端（毛先）へのグラデーションにする
- 色の置き換えや描き換えの後は、マテリアルの乗算色を白に戻し、影の色は作者の明暗比を保った灰色にする。発光色（例: ピンクの髪のオレンジのツヤ）は、強さを保ったまま新しい色の色相に合わせる（`useTextureColors`）
- **画像生成での描き換え方はマテリアルごとに決める**（`repaintMode`、`shared/protocol.ts`）。顔のパーツはマテリアル名から見分ける（`facePart`: `EyeIris` → 瞳、`FaceBrow` → 眉、`Face_00_SKIN` → 顔の肌など）
  - `paint`（服・靴・小物、瞳の虹彩）: 使っている島の中だけ描き換え、元のアルファを戻す
  - `shape`（眉・まつげ・アイラインで、形がテクスチャに描かれているもの）: 線をグレーで描き直させ、マゼンタのキーを透明に戻して新しい線の形にする（`keyAlphaPixels`）。色はその後の色の置き換えで付ける。線の量（アルファの平均）が元の 2.5 倍を超えたり 1/5 未満になったりしたら採用しない（`shapeRejection`）。形がテクスチャに描かれているかは、アルファで切り抜く設定で、かつ UV の範囲の 15% 以上が透明かどうかで判定する（`drawnShape`）。平たい帯のテクスチャ（形はメッシュ）は色の置き換えだけ
  - `overlay`（顔の肌）: 描き足しを頼み、元との差が大きい画素だけを、ぼかしてなじませて取り込む。元の輪郭（近傍との明暗差が大きい画素）の変化は、描き直しのずれとして捨てる。変化が使っている範囲の 25% を超えたら採用しない（`overlayWeights`）
  - 髪・体の肌・白目・ハイライト・口は画像生成に回さない（全面が縦グラデーションの髪のアトラスに、市松模様の上の毛束を描くなど、絵として描き直されるため）
- **顔のパーツには参照画像を渡さない**。参照画像を渡すと、瞳の中にキャラクターの絵を描き込んだ。Neon が文章で色・形・位置を指示する
- **小さな島は切り出して送る**（`usedBounds` / `frameAtlas`）。使っている範囲を囲む矩形を、画像モデルが受け付ける縦横比になるようマゼンタで広げ、長辺 1024 px まで拡大して送る。結果は元の矩形に戻して貼る。空いたアトラスに小さな島だけがあると、画像モデルはそこを画用紙とみなして絵を描く
- **オッドアイ**: 瞳の UV 三角形を、頭より左（+X）か右かで分ける（`uvMask` の `side`、`leftEyeSide`）。左右の島が別なら、左目の島だけ別の色に置き換える。左右が同じ島を共有するモデル（VRM1 Twist Sample）は `shared` と判定し、オッドアイの指定を捨てる
- **UV マスク**（`VrmAvatar.uvMask`）: そのアトラスを使うメッシュの UV 三角形を塗って、使われている範囲（数 px 広げる）を求める。画像モデルにはマスク外をマゼンタで塗って送り、結果はマスク内だけ元のアトラスに合成し、元のアルファを戻す（`keyUnused` / `composeRepaint`）。余白に描かれた模様や島の外へのはみ出しはモデルに映らない。三角形は向きをそろえて塗る（左右対称の服で裏返しの島が重なっても穴が開かない）
- 同じアトラスを共有するマテリアル（例: Seed-san の `wear`）は、1 回の描き換えをまとめて適用する
- **素体の候補**は同梱 6 体（`SAMPLE_AVATARS` の `traits` に髪型・体格・袖の長さ・付属品を書く）。選んだ素体の `traits` は仕様づくりの呼び出しにも渡し（`baseTraits`）、Neon が「半袖の素体に長袖」「素体にだけあるネクタイ」を判断できるようにする
- **腕・脚の服**（`bodyPaint`、`VrmAvatar.limbMask`）: 体の肌（SKIN で顔以外）のメッシュの三角形のうち、上腕・前腕（または太もも・すね）とその補助ボーン（VRoid の `J_Sec_*`）の重みが平均 0.5 以上のものを UV に塗って範囲を作る。手・足のボーンの手前で止まるので、袖は手首、裾は足首で終わる。範囲内だけを服の色に置き換える（陰影は肌のもの）
- **パーツを消す**（`hide`）: 服・小物（CLOTH / OTHER で顔のパーツ以外）だけ。画面では `material.visible = false`、書き出しではマテリアルを MASK・アルファ 0 にする（VRM 0.x は `_ALPHATEST_ON`、`_BlendMode` 1、`_Cutoff`、`_Color` のアルファ）。メッシュとテクスチャは残すので、元に戻すのも簡単

## 実行の記録（`server/runlog.ts`）

開発時（`NODE_ENV` が production 以外、または `VTUBER_DIAG=1`）は、`generate()` の呼び出しごとに役割・モデル・秒数・画像の枚数・トークン数（入力・出力・思考）・終了理由・外した設定・エラーを `logs/gemini.jsonl` に書き、サーバーの出力にも 1 行出す。クライアントは書き起こし・アバター設計の実行ごとに、手順の最終状態・適用した仕様・問題点を `POST /api/log` で送り、`logs/transcribe.jsonl` に追記する。画像は記録しない

## .vrm の書き出し（`VrmExport.ts`）

読み込んだファイルのバイト列を保持しておき、変えた部分だけを書き換えた GLB を作る。メッシュ・スケルトン・表情・揺れ物・コンストレイント・利用条件はバイト単位でそのまま残る。

- 変えたマテリアルは、three.js のマテリアルと GLTFLoader の対応表（`parser.associations`）から元のマテリアル番号を引く
- VRM 1.0 は glTF の `baseColorFactor` と `VRMC_materials_mtoon` にリニアの値を書く。VRM 0.x は `materialProperties` の `_Color` などにガンマの値（`pow(v, 1/2.2)`。three-vrm は `pow(v, 2.2)` で読む）を書く
- テクスチャは、その画像を読むマテリアルがすべて同じ描き換えを受けたときだけ差し替える。変えていないマテリアルと共有している画像は、複製して付け替える
- バッファビューは元のオフセットの 4 の剰余を保って詰め直す（アクセサの境界を崩さない）。名前（`meta.name` / `meta.title`）とサムネイルも差し替える。頭の小物は three.js の図形なので書き出さない

| 新しい入力（画面共有、WebRTC、仮想カメラ） | `FrameSource` | `App.setSource()` |
| 新しいトラッカー（視線専用モデル、物体検出、外部トラッカー） | `Tracker` | `TrackerHost.add()`（`src/main.ts`） |
| 別形式のアバター（Live2D、独自ボーンマップの glTF） | `AvatarRig` | `App.setAvatar()` |
| 機能・演出（BGM、コメント連携、エフェクト） | `Plugin`（`setup` / `update`） | `app.use()`（`src/main.ts`） |
| 新しい Gemini ロール | `server/gemini/<name>.ts` の `RouteHandler` | `API_ROUTES`（`server/index.ts`）＋ `config/models.json` ＋ `ModelRole` |
| 新しい Live ツール | 宣言と検証（`server/gemini/live.ts`）＋ `LiveToolCall` 型 | クライアント側は `LiveDirectorPlugin.onMessage` |

候補として、`lyria-realtime-exp`（BGM のリアルタイム生成）や `gemini-robotics-er-2-streaming-preview`
（物体の連続追跡）は、同じ手順でロールとプラグインを追加すれば組み込める。

## セキュリティ

- API キーはサーバー側だけで使う。ブラウザには渡らない。
- サーバーは既定で `127.0.0.1` にだけ待ち受ける。さらに Host ヘッダの許可リスト（DNS リバインディング
  対策）と Origin の一致を確認する（CSRF と WebSocket ハイジャック対策）。LAN に公開する場合は
  `HOST` と `ALLOWED_HOSTS` を明示する。この API は利用者の Gemini 課金を代行するので、公開範囲に注意する。
